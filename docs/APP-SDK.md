# Atrium application platform

Status: initial design of the manifest format and the application lifecycle.
Manifest schema version `1` is a draft until Alpha 0.1 ships one application
through the whole pipeline; after that it is versioned and additive.

## Why a manifest

The prototype proves the failure mode this design exists to avoid. It has
service-specific code for Homarr, Glances and qBittorrent — separate Rust
modules, separate credential adapters, separate response parsers, separate UI
surfaces. Each one is well built and each one is a permanent maintenance debt.
Adding the fourth service means writing the fourth module.

The rule for the platform: **adding an application to the catalogue must be a
data change, not a code change.** If a new app needs new UI logic, either the
manifest schema is missing a concept, or that app does not belong in the
catalogue yet.

## Model

```
Catalogue entry  →  Manifest (versioned, signed)
                       +
                 User settings (validated against the manifest's schema)
                       +
                 Allocated resources (ports, volumes, secrets, network)
                       ↓
                 ContainerSpec  →  ContainerProvider  →  running app
```

**Agent** composes the `ContainerSpec`, from the signed manifest, after verifying
the signature against the catalogue publisher trust root compiled into it
(ADR-014, ADR-016). Core resolves the user's choices into an
install intent and passes it along; the specification Core would compute is used
only to *preview* ports and volumes in the UI, and is never applied. The manifest
never contains a container command line, a host path, or anything copied through
unvalidated.

## Manifest — draft v1

```yaml
schemaVersion: 1

metadata:
  id: jellyfin                      # stable, immutable, [a-z0-9-], used in paths and labels
  name: Jellyfin
  version: "10.10.3"                # upstream version, for display
  revision: 4                       # this manifest's revision; increments on any change
  tagline: Movies, series and music from your own library
  description: |
    A media server that streams your library to browsers, phones and televisions.
  categories: [media]
  homepage: https://jellyfin.org
  license: GPL-2.0-only
  icon: icons/jellyfin.svg          # inert SVG/WebP inside the catalogue, no remote URL
  screenshots: [screenshots/library.webp]
  maintainer: atrium-catalog        # catalogue curator, not the upstream project

requirements:
  atriumVersion: ">=0.1.0"
  architectures: [amd64, arm64]
  minMemoryMb: 512
  minDiskMb: 2048
  capabilities: []                  # host capabilities that must be present, e.g. [smart]

runtime:
  kind: container                   # the only kind in v1
  restartPolicy: unless-stopped
  user: "1000:1000"                 # or "image-default"
  readOnlyRootFilesystem: false     # true where the image supports it
  images:
    - name: app
      reference: docker.io/jellyfin/jellyfin
      digest: sha256:0f2a...        # resolved and pinned by the catalogue build, required
      platforms: [linux/amd64, linux/arm64]

network:
  mode: bridge                      # bridge | app-private ; host is a declared capability
  ports:
    - id: http
      container: 8096
      protocol: tcp
      suggestedHost: 8096           # a suggestion; Core allocates and may choose another
      primary: true                 # the one the "Open" button uses
      exposure: lan                 # lan | loopback

volumes:
  - id: config
    container: /config
    kind: appdata                   # appdata | media | scratch
    minSizeMb: 256
    backup: always                  # always | optional | never
  - id: media
    container: /media
    kind: media
    mode: ro
    required: true
    prompt:
      label: Media library
      help: The folder Jellyfin should scan. Atrium will not modify it.

settings:                            # user-facing configuration, rendered as a form
  - key: TZ
    label: Time zone
    type: timezone
    default: from-host
    env: TZ
  - key: publishedUrl
    label: External address
    type: string
    optional: true
    pattern: '^https?://[^\s]+$'
    env: JELLYFIN_PublishedServerUrl

secrets:                             # generated by Core; never in the manifest, never returned by the API
  - key: apiKey
    generate: { kind: hex, bytes: 32 }
    env: ATRIUM_APP_API_KEY
    rotatable: true

permissions:                         # declared here — and in Alpha, every one of these must be empty
  hostPaths: []                      # REFUSED in Alpha; needs a console grant (ADR-014)
  devices: []                        # REFUSED in Alpha; this is why there is no GPU transcoding yet
  hostNetwork: false                 # REFUSED in Alpha
  privileged: false                  # REFUSED in Alpha
  addCapabilities: []                # REFUSED in Alpha
  atriumApi: none                    # REFUSED in Alpha; an app talking to Core is exceptional

health:
  readiness:
    kind: http
    path: /health
    port: http
    expectStatus: [200]
    intervalSeconds: 10
    timeoutSeconds: 3
    failureThreshold: 6
  liveness:
    kind: tcp
    port: http
    intervalSeconds: 30

dependencies:
  services: []                       # other catalogue apps this one needs, e.g. [{ id: postgres, version: ">=15" }]
  optional: []

lifecycle:
  upgrade:
    strategy: recreate               # recreate | in-place
    preflight:
      - kind: backup-volumes
        volumes: [config]
    breakingFrom: ["<10.9.0"]        # versions that need a migration note shown before upgrade
  uninstall:
    dataDefault: keep                # keep | remove — the owner always chooses, this is the pre-selection
    warnings:
      - Removing data deletes Jellyfin's watch history and user accounts.

backup:
  include: [config]
  exclude: [media]
  quiesce:
    stopBeforeBackup: true           # simplest correct behaviour in v1

ui:
  entry:
    port: http
    path: /
    openIn: embedded                 # embedded | browser
  authHandoff: none                  # none | basic | none-documented — never generic form injection
```

### Fields that do not exist, on purpose

- No `command`, `entrypoint`, `args`, or anything else that becomes process argv.
- No arbitrary host path without a `permissions.hostPaths` declaration and owner
  consent.
- No `image: latest`. A manifest without a digest does not validate.
- No hook that executes a script on the host. Lifecycle hooks are typed
  operations from a closed set (`backup-volumes`, `stop-app`, `wait-healthy`), not
  shell.
- No remote URL for icons, fonts or any other asset. Catalogue content is local
  and inert — the rule the prototype's theme packs already follow.

## Validation

A manifest is rejected — at catalogue build time and again at install time — if:

- the schema version is unknown, an unknown field is present, or a required field
  is missing (the prototype's strict-parsing rule, kept)
- any image lacks a digest, or the digest does not resolve for the host
  architecture
- a port is privileged (<1024) without a declared reason, or duplicates another
  port in the same manifest
- a volume's container path is not absolute, or escapes with `..`
- a setting's `env` name collides with a secret's, or with a reserved `ATRIUM_*`
  name
- `permissions` requests anything at all — in Alpha the entire block must be empty
  or false, and Agent refuses the operation if a derived specification would
  contain a host path, a device, host networking, an added capability, privileged
  mode, or access to Atrium's API (ADR-014)
- the manifest is unsigned or its signature does not verify, checked by the
  catalogue build, by Core, **and independently by Agent**

## Installation

1. **Resolve** — fetch the manifest from the catalogue, verify the signature,
   check `requirements` against `GET /api/v1/system/capabilities`. Unmet
   requirements produce a specific, readable refusal, not a greyed-out button
   with no reason.
2. **Configure** — render `settings` and any `prompt`-bearing volumes as a form.
   Validate client-side for feedback and server-side for truth.
3. **Consent** — the screen that shows what a permission lets an app do, in plain
   language, with an explicit acceptance that is never skippable and never
   pre-accepted. In Alpha it never appears, because no manifest may request a
   permission. It is designed now so that the mechanism exists before the need
   does — and when permissions return, the *authority* comes from an owner grant
   made at the server console, which Agent can verify, not from this screen, which
   a compromised Core could fabricate (ADR-014).
4. **Allocate** — pick host ports (avoiding conflicts with the host and other
   apps), create volumes under the app's data root, generate secrets, create the
   app's network.
5. **Pull** — by digest, with progress reported on the operation.
6. **Apply** — Agent derives the `ContainerSpec` from the signed manifest, enforces
   the Alpha constraint set, creates the container, stamps
   `io.atrium.managed=true`, `io.atrium.app=<id>` and an owner token Core never
   sees, and records the result in its own ownership registry (ADR-013).
7. **Enable** — register with `ServiceProvider` so the app returns after a reboot.
8. **Verify** — run the readiness check until healthy or the threshold is hit.
9. **Settle** — `running` or `unhealthy`. Never a silent partial install; a failure
   at any step rolls back to the previous clean state and reports which step failed.

## Upgrade

- The catalogue's newer manifest revision is compared to the installed one. The
  diff shown to the owner names what changes: image version, new settings, new
  permissions, removed settings.
- **A permission increase is never applied silently.** It requires the consent
  screen again.
- `preflight` runs first — for `recreate`, that means backing up the declared
  volumes.
- The old container is kept until the new one passes readiness; failure restores
  the previous revision and its volumes.
- `breakingFrom` shows an upstream migration notice before anything happens.
- Settings whose schema changed are migrated where the manifest declares a
  mapping, and surfaced for review where it does not.

## Uninstall

- Stop, disable, remove container, remove network, release ports.
- Data: the owner explicitly chooses keep or remove. `dataDefault` only sets the
  pre-selection. Removing data requires the destructive-confirmation flow from
  [`SECURITY.md`](SECURITY.md#7-authorization).
- Kept data remains under the app's data root and is offered back if the app is
  reinstalled.
- Secrets for a removed app are deleted with the app record, following the
  prototype's credential-cleanup journal pattern: the intent is recorded durably
  before deletion, retried on failure, and visible as a recovery state if it never
  succeeds.

## Backup integration

An app declares what matters. The platform's backup engine (post-Alpha) reads
`backup.include`, quiesces per `quiesce`, and produces a restorable set. Restore
re-creates the volumes and then re-applies the container spec — it never restores
a container image.

## UI integration

- `ui.entry` gives the dashboard an "Open" target. The desktop client opens it as
  an embedded WebView with a persistent per-app profile, which is exactly what the
  prototype already does well; the web client opens a new tab.
- Icon, categories, tagline and health come from the manifest, so the app tile
  needs no per-app code.
- `authHandoff` is deliberately almost always `none`. Atrium does not inject
  credentials into arbitrary pages. Where an app supports a documented handoff it
  gets a named adapter, reviewed individually — the prototype's rule, unchanged.

## Catalogue

- A signed, versioned artefact containing manifests and their inert assets.
- Bundled with the Core release in Alpha; an optional pinned remote catalogue
  later.
- Curated by this project, and deliberately small: **roughly ten applications at
  Beta** (A-15). No third-party publishing, no user-submitted manifests in the UI,
  no marketplace — see [`PRODUCT.md`](PRODUCT.md#non-goals).
- The catalogue is signed by a **catalogue publisher key** whose public half is
  compiled into the Agent binary. It is a different key from the release signing
  key and from any server's device identity key, and Core can neither supply it
  nor replace it (ADR-016). Verification is one Ed25519 signature over
  `index.json`, plus a digest check of each manifest against that verified index.
- A local manifest may be installed from a file for development, behind a setting
  that is off by default and clearly labelled as unverified.

## Deliberately deferred

- Every `permissions` field, as above. Hardware transcoding is the painful one and
  is named explicitly in [ADR-014](adr/0014-agent-enforced-container-specs.md).
- Adoption of containers the user created. They stay read-only until a workflow
  exists whose authority Agent can verify.

- Multi-container applications (an app plus its database) beyond the
  `dependencies` field's simplest form.
- Manifest-declared reverse-proxy routes and per-app subdomains.
- Resource limits (CPU shares, memory caps) — designed later, not guessed now.
- App-to-app communication beyond declared dependencies.
- Community catalogues, publishing tooling, a manifest linter as a public product.
